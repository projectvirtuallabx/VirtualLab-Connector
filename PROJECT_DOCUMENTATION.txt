1. EXECUTIVE SUMMARY AND PROJECT AIM
================================================================================

The VirtualLab-Connector is a Python-based middleware service that bridges a
cloud-hosted VirtualLab booking backend with a MeshCentral remote-management
server. Its primary purpose is to automate the lifecycle of remote desktop
(RDP) access for virtual lab bookings.

AIM OF THE PROJECT
------------------
  - Receive booking tasks from the VirtualLab Node.js backend.
  - Generate time-limited MeshCentral device-sharing (guest desktop) links
    for the correct lab machine using the meshctrl CLI.
  - Deliver the RDP link to the end user via email (SMTP).
  - Report results (RDP link, share ID, success/failure) back to the backend
    so bookings can be updated in the database.
  - Revoke MeshCentral shares when bookings are cancelled or deleted.

The connector replaces earlier Node.js logic for MeshCentral link generation
and email delivery, centralizing that responsibility in a single Python
service that can run on a Windows host co-located with MeshCentral and
meshctrl.

================================================================================
2. PROBLEM STATEMENT AND SOLUTION OVERVIEW
================================================================================

PROBLEM
-------
Virtual lab users book time slots on physical or virtual lab machines. After
a booking is confirmed, they need a secure, time-bound remote desktop URL.
Creating and revoking these links manually is error-prone. The main backend
(cannot run meshctrl directly) must delegate MeshCentral operations to a
trusted agent.

SOLUTION
--------
A dedicated connector process:
  1. Polls the backend for pending connector tasks (default mode), OR
     accepts tasks via HTTP (Flask mode) or CLI (testing).
  2. Invokes meshctrl (Node.js) against the MeshCentral server.
  3. Parses the RDP URL and share identifier from command output.
  4. Sends a formatted email to the user.
  5. POSTs a structured JSON result to the backend callback endpoint.

7. DATA MODELS
================================================================================

7.1 ConnectorTaskType (Enum)
----------------------------
  BOOKING_CREATE  - treated same as GENERATE_RDP (create share + email)
  BOOKING_DELETE  - revoke MeshCentral share
  GENERATE_RDP    - default; generate link and email user
  FILE_TRANSFER   - stub (not implemented)
  STATUS_UPDATE   - stub (not implemented)

7.2 BookingPayload (Inbound)
----------------------------
  Field              Type        Required  Description
  -----------------  ----------  --------  ----------------------------------
  bookingId          string      yes       Unique booking identifier
  userId             string      yes       User identifier in backend DB
  userEmail          string      yes       Recipient for RDP email
  labName            string      yes       e.g. "FROST Lab"
  start              string      yes       ISO 8601 booking start time
  end                string      yes       ISO 8601 booking end time
  durationMinutes    int         yes       Share duration for meshctrl
  meshNodeId         string      no*       MeshCentral device node ID
  shareId            string      no        Required for BOOKING_DELETE
  callbackUrl        string      no        Override default callback URL
  taskType           string      no        Default: GENERATE_RDP

  * meshNodeId resolved from LAB_NODE_MAP when labName is known; otherwise
    must be supplied in payload.

7.3 ConnectorResult (Outbound)
------------------------------
  Field       Type        Description
  ----------  ----------  --------------------------------------------------
  bookingId   string      Same as inbound booking
  rdpLink     string|null HTTPS RDP/guest URL (null on delete/failure)
  success     bool        true if primary operation succeeded
  error       string|null Semicolon-separated error messages if any
  stdout      string      meshctrl standard output (debug/audit)
  stderr      string      meshctrl standard error (debug/audit)
  shareId     string|null MeshCentral share ID for later revocation

8. TASK TYPES AND BUSINESS LOGIC
================================================================================

8.1 GENERATE_RDP / BOOKING_CREATE
---------------------------------
  Steps:
    1. Convert booking start time from UTC ISO to local timezone string.
    2. Resolve mesh node ID from LAB_NODE_MAP or payload.
    3. Run: meshctrl devicesharing --add guest --type desktop ...
    4. Parse URL: line or first https URL in output.
    5. Parse shareId from output.
    6. If link exists, send email to userEmail.
    7. success = true if rdpLink was generated (email failure recorded in
       error but does not flip success to false).
    8. POST ConnectorResult to backend callback.

8.2 BOOKING_DELETE
------------------
  Two revocation strategies:

  Path A - shareId provided in payload:
    Run meshctrl devicesharing --remove <shareId>

  Path B - shareId missing:
    List all shares on the node, then remove each share ID found.
    Returns success if at least one removal succeeds.

  Result posted to backend with rdpLink=null.

8.3 FILE_TRANSFER / STATUS_UPDATE
---------------------------------
  Placeholder handlers return success=false with "not yet implemented"
  and still POST result to backend for observability.

9.3 RDP LINK GENERATION (meshctrl)
----------------------------------

    def generate_rdp_link(payload: BookingPayload):
        utc_time   = datetime.fromisoformat(payload.start.replace("Z", "+00:00"))
        local_time = utc_time.astimezone()
        start_str  = local_time.strftime("%Y-%m-%dT%H:%M:%S")

        mesh_node_id = LAB_NODE_MAP.get(payload.labName, payload.meshNodeId)

        cmd = [
            "node", MESHCTRL_PATH, "devicesharing",
            "--url", MESHCENTRAL_URL,
            "--loginuser", MESHCENTRAL_USER,
            "--loginpass", MESHCENTRAL_PASS,
            "--id", mesh_node_id,
            "--add", "guest",
            "--type", "desktop",
            "--start", start_str,
            "--duration", str(payload.durationMinutes),
        ]
        returncode, stdout, stderr = _run_meshctrl(cmd)
        # Parse "URL:" line or regex https URL from output
        # Parse shareId for backend storage and future revocation
        return rdp_link, share_id, stdout, stderr


9.4 BACKEND CALLBACK
--------------------

    def post_result_to_backend(result: ConnectorResult,
                               callback_url: Optional[str] = None) -> bool:
        url     = callback_url or BACKEND_CALLBACK_URL
        headers = {
            "Content-Type":  "application/json",
            "Authorization": f"Bearer {SECRET_TOKEN}",
        }
        resp = requests.post(url, json=asdict(result), headers=headers, timeout=15)
        resp.raise_for_status()
        return True

    def poll_backend() -> None:
        while True:
            resp = requests.get(BACKEND_POLL_URL, headers=headers, timeout=10)

10. BACKEND INTEGRATION (POLL AND CALLBACK)
================================================================================

10.1 POLL ENDPOINT (Connector -> Backend)
-----------------------------------------
  Method   : GET
  URL      : BACKEND_POLL_URL
  Headers  : Authorization: Bearer <SECRET_TOKEN>
             Content-Type: application/json

  Expected responses:
    200 + empty/null body     No pending task; connector sleeps 5s
    200 + JSON task object    Process immediately via dispatch_task()
    401                       Token mismatch; logged as error

  Example task body (GENERATE_RDP):
  {
    "bookingId": "bk_abc123",
    "userId": "user_001",
    "userEmail": "student@university.edu",
    "labName": "FROST Lab",
    "start": "2026-05-20T10:00:00.000Z",
    "end": "2026-05-20T12:00:00.000Z",
    "durationMinutes": 120,
    "taskType": "GENERATE_RDP"
  }

  Example task body (BOOKING_DELETE):
  {
    "bookingId": "bk_abc123",
    "userId": "user_001",
    "userEmail": "student@university.edu",
    "labName": "FROST Lab",
    "start": "2026-05-20T10:00:00.000Z",
    "end": "2026-05-20T12:00:00.000Z",
    "durationMinutes": 120,
    "shareId": "share_xyz789",
    "taskType": "BOOKING_DELETE"
  }

10.2 CALLBACK ENDPOINT (Connector -> Backend)
---------------------------------------------
  Method   : POST
  URL      : BACKEND_CALLBACK_URL (or per-task callbackUrl)
  Headers  : Same Bearer token
  Body     : JSON serialization of ConnectorResult

  Example success callback:
  {
    "bookingId": "bk_abc123",
    "rdpLink": "https://mesh.example.com/?view=...&guest=...",
    "success": true,
    "error": null,
    "stdout": "... meshctrl output ...",
    "stderr": "",
    "shareId": "share_xyz789"
  }

  Example failure callback:
  {
    "bookingId": "bk_abc123",
    "rdpLink": null,
    "success": false,
    "error": "Failed to generate RDP link.",
    "stdout": "",
    "stderr": "login failed",
    "shareId": null
  }

  Backend responsibility: persist rdpLink and shareId on the booking record,
  update booking status, and expose the link in the user-facing application.

11. MESHCENTRAL INTEGRATION
================================================================================

11.1 meshctrl execution
-----------------------
  Commands run via subprocess:
    - Working directory: MESHCTRL_CWD (e.g. D:\mesh)
    - Executable: node <MESHCTRL_PATH> <subcommand> [flags]
    - Timeout: 60 seconds

11.2 Create share command (conceptual)
--------------------------------------
  node meshctrl.js devicesharing
    --url wss://mesh.virtuallabx.com
    --loginuser <admin>
    --loginpass <password>
    --id <node_id>
    --add guest
    --type desktop
    --start 2026-05-20T15:30:00
    --duration 120

11.3 Output parsing
-------------------
  Primary: line starting with "URL:" contains the guest RDP link.
  Fallback: regex search for first http(s) URL in combined stdout+stderr.
  shareId: lines like "ShareID: ..." or "id: ..." (case-insensitive).

11.4 Lab to node mapping
------------------------
  Only labs listed in LAB_NODE_MAP are auto-resolved. To add a new lab,
  insert an entry:

    LAB_NODE_MAP["New Lab Name"] = "<meshcentral_device_node_id>"

  Alternatively, pass meshNodeId explicitly in the task payload.

12. EMAIL NOTIFICATION SYSTEM
================================================================================

When an RDP link is successfully generated:
  - SMTP server: smtp.gmail.com:587 with STARTTLS
  - From: SENDER_EMAIL
  - To: payload.userEmail
  - Subject: "Your VirtualLab RDP Link - {labName}"
  - Body: plain text + HTML table with link, booking ID, start, end

Email failure is appended to ConnectorResult.error but success remains true
if the link was generated, ensuring the backend still receives the URL.

14. HTTP API REFERENCE (FLASK MODE)
================================================================================

Authentication: Authorization: Bearer <SECRET_TOKEN> on all endpoints below.

POST /connector/generate-rdp
  Body: BookingPayload JSON
  Response: ConnectorResult JSON
  Status: 200 if success, 500 if link generation failed

POST /connector/task
  Body: BookingPayload JSON (taskType selects handler)
  Response: ConnectorResult JSON
  Status: 200 if success, 500 on failure

GET /health
  Response: {"status": "ok"}
  No authentication required in current implementation

Note: Flask mode still calls post_result_to_backend() after processing, so
the backend receives both the HTTP response and the callback POST.

17. SECURITY CONSIDERATIONS
================================================================================

  - Credentials (SMTP, MeshCentral, SECRET_TOKEN) are currently stored in
    source code. For production, move to environment variables or a secrets
    manager and never commit real passwords to version control.
  - Bearer token must match between connector and backend on poll/callback.
  - RDP guest links are time-limited per meshctrl --duration and --start.
  - Revocation on BOOKING_DELETE limits exposure after booking ends.
  - Consider restricting Flask --serve to localhost or a private network.
  - stdout/stderr in callbacks may contain sensitive meshctrl output; backend
    should avoid exposing raw logs to end users.

================================================================================
18. ERROR HANDLING AND LOGGING
================================================================================

  - Python logging module: INFO level, timestamped messages.
  - meshctrl failures: captured in stdout/stderr fields of ConnectorResult.
  - subprocess timeout: 60s, returns error string in stderr.
  - Payload validation: ValueError with missing field list; poll loop logs
    and continues without crashing.
  - HTTP 401 on poll: logged as SECRET_TOKEN mismatch.
  - Backend POST failures: logged; connector does not retry automatically.
  - Email exceptions: returned as error string, included in result.error.

================================================================================
19. LIMITATIONS AND FUTURE ENHANCEMENTS
================================================================================

CURRENT LIMITATIONS
  - Single-file monolith; no unit tests in repository.
  - FILE_TRANSFER and STATUS_UPDATE task types are not implemented.
  - Poll loop has fixed 5-second interval; no exponential backoff.
  - Callback POST has no retry mechanism on network failure.
  - Hardcoded configuration requires code edit to change environments.
  - Connector host must be Windows-oriented paths (D:\mesh) as written.
  - BOOKING_DELETE without shareId removes ALL shares on a node (aggressive).

PLANNED / SUGGESTED ENHANCEMENTS
  - Externalize all secrets to .env or OS environment variables.
  - Implement FILE_TRANSFER and STATUS_UPDATE handlers.
  - Add retry with backoff for backend callback.
  - Support multiple labs without code changes (backend supplies meshNodeId).
  - Docker or systemd service definition for production uptime.
  - Structured metrics / health reporting beyond GET /health.
  - Redact or truncate stdout/stderr in production callbacks.

================================================================================
20. CONCLUSION
================================================================================

The VirtualLab-Connector is a focused integration service that automates
MeshCentral guest desktop sharing for virtual lab bookings. It closes the
gap between a cloud booking API and on-premise remote access infrastructure
by generating RDP links, notifying users by email, and synchronizing results
with the central backend.

Its three execution modes (poll, HTTP, CLI) support production deployment,
push-based integration, and developer testing. The task-type enum and payload
schema are designed for extension as VirtualLab adds file transfer and status
features.

This document, together with connector.py, provides a complete reference for
understanding, deploying, and maintaining the VirtualLab MeshCentral Connector.
